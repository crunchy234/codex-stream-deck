# T3 Code thread keys

Agent 1–6 can monitor T3 Code threads and open them in the T3 desktop app. This source works independently of the Codex renderer bridge. It uses T3's authenticated, read-only protocol-2 HTTP shell snapshot and native `t3code://threads/<environment>/<thread>` links. No T3 files are patched and no task database is read.

## Setup

Use a recent T3 Code desktop build that supports orchestration protocol 2 and thread deep links. Open T3 Code once so its local server and `t3` CLI are available. From this repository:

```sh
npm ci
npm run setup:t3
npm run pack
```

Open the resulting Stream Deck plugin package in `dist/`, then choose **T3 Code threads** under **Agent source** in any Agent key's property inspector. This source selection applies to all six Agent keys. A Codex launcher is not required for T3 thread keys.

Setup creates a bearer session with only `orchestration:read`, valid for 30 days, and saves its credential outside the repository:

- macOS: `~/Library/Application Support/CodexDeck/t3.json`
- Windows: `%LOCALAPPDATA%\CodexDeck\t3.json`

The file is written with owner-only permissions on systems supporting POSIX permissions. Keep it private; on Windows it inherits its containing directory's ACL. Run setup again when the credential expires or is revoked. The plugin reloads the configuration on its next poll; no restart is needed.

On macOS, setup defaults to `~/.t3/bin/t3`. On Windows it looks for `t3` on PATH. To use a standalone CLI executable, another T3 home, a development build, or a different session lifetime:

```sh
npm run setup:t3 -- --cli /path/to/t3 --base-dir /path/to/t3-home --ttl 30d
npm run setup:t3 -- --scheme t3code-dev
```

`--cli` must identify an executable that can run directly, rather than a Windows `.cmd` wrapper. `--base-dir` is T3's base directory containing `userdata/`. `--runtime` overrides the full path to `server-runtime.json`; `--output` overrides the credential configuration destination for testing.

## Thread assignments and states

Pin threads in T3 to choose your keys. Agent 1–6 follow the first six pins in T3's explicit pinned order. Reordering or unpinning in T3 updates the keys. Unused keys stay empty. Subagents are excluded from automatic assignments even when they carry inherited pin metadata.

With no pinned threads, the plugin fills six keys from active, non-settled, non-subagent threads. Their positions remain stable as titles and activity change. A removed, archived, or settled thread frees its position for another active thread. Pin threads for predictable assignments across plugin restarts.

For fixed assignments, add a `threadIds` array to `t3.json`, containing up to six thread IDs or `null` for empty positions. IDs come from the thread's copied T3 link (decode the final URL path segment). Explicit assignments take precedence over pinning. An unavailable assigned thread leaves its key empty instead of opening another thread. Setup preserves these assignments when renewing access to the same environment.

Tiles show the thread title and existing status animation:

- Working: preparing, queued, starting, running, or waiting for agent work.
- Needs input: a runtime request or actionable proposed plan.
- Error: a failed run.
- Unread completion: a completed run newer than T3's last-visited timestamp or this plugin session's last button press.
- Idle: other available threads.

Pressing a tile opens that exact thread and brings T3 forward. A hold has no extra action. T3's server-side visited timestamps acknowledge threads opened in the app too. There is no selected-thread outline because the shell API does not report which thread is currently displayed. Context rings are unavailable for this source.

The local snapshot refreshes approximately every 1.2 seconds, plus request time. During an outage, last-known tiles remain visible with offline styling and cannot switch threads. Monitoring resumes when the app returns; the runtime file supplies its current port. The credential is sent only over loopback HTTP, never through a redirect, and only after checking the environment identity and protocol version.

Only the six Stream Deck agent keys use this source. Other action keys still control Codex. T3 monitoring is local to the Stream Deck computer; it does not extend to the multi-host relay or iPhone companion.

## Compatibility and verification

Version 0.7.0.16 fixes imported thread IDs containing encoded paths or more than 200 characters causing the entire monitor to go offline. Existing read-only access remains valid; reinstall the newer plugin without rerunning setup.

This integration depends on T3's current shell HTTP contract and desktop deep-link handler. Older versions without protocol 2 are reported as unavailable. Test fixtures cover state mapping, imported thread IDs, assignments, authorization, redirects, disconnects, and recovery. A live desktop check is separate from physical Stream Deck testing.
